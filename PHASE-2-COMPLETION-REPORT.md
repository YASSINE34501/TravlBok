# TravlBok — Phase 2 Completion Report

**Scope:** Subscriptions, Payments, Affiliates, and Hotel PMS, per `MASTER-PLAN.md`.
**Status:** In progress — delivered as 4 sub-milestones, each with its own verification pass and commit. This report is appended to as each milestone lands.

---

## Milestone 1 — Subscriptions

### What was built
- **Schema**: `SubscriptionPlan` (tier, localized name/description, monthly/annual price, trial days, per-metric limits — properties/rooms-per-property/vehicles/branches/staff/monthly-bookings, 8 feature flags, archive flag), `Subscription` (one per `Organization`, status lifecycle `TRIALING → ACTIVE → PAST_DUE/GRACE_PERIOD → SUSPENDED/CANCELLED/EXPIRED`, billing interval, period dates, cancel-at-period-end), `UsageRecord` (append-only usage snapshot log for future reporting — never consulted for limit decisions, which always re-count live rows). `CouponScope` gained a `SUBSCRIPTION` value for future subscription coupon codes.
- **Limit enforcement**: a single shared helper, `src/domains/subscriptions/limits.ts` (`checkOrganizationLimit`, `hasFeature`), wired into every real creation choke point: `createHotelAction` (properties), `createVehicleAction` (vehicles), `createBranchAction` (branches), `createRoomAction` (rooms per property), and both `createHotelReservationAction`/`createCarReservationAction` (monthly bookings, checked inside the existing transaction). A suspended/expired subscription blocks regardless of numeric usage.
- **Staff**: no "invite a team member" action existed anywhere in the codebase before this milestone — added `src/domains/staff/actions.ts` (`inviteStaffMemberAction`/`removeStaffMemberAction`) as the `STAFF` limit's choke point, plus a real partner-dashboard screen (`dashboard/staff`) — not a placeholder, it lists current members and lets an owner invite an already-registered user by email into a hotel/car-rental staff role.
- **Lifecycle**: `registerAction` now auto-assigns the seeded FREE plan to every new hotel/car-rental/travel-agency organization inside its existing transaction. `src/domains/subscriptions/actions.ts` adds `changePlanAction` (blocks a downgrade that would immediately exceed the target plan's limits), `cancelSubscriptionAction` (soft cancel via `cancelAtPeriodEnd`), and `renewSubscriptionAction` (platform-staff only, for the future billing-cycle job Payments will drive).
- **Admin**: `admin/subscription-plans` (create/archive plans, full limit + feature-flag editor) and `admin/subscriptions` (list all orgs' subscriptions, manual assignment, suspend, an estimated-MRR summary card).
- **Partner**: `dashboard/subscription` shows the current plan/status/renewal date and lets an owner change plan/billing interval or cancel.
- **Seed data**: 5 real plans (Free/Starter/Professional/Business/Enterprise) with realistic limits and feature flags; the two demo organizations get Professional and Starter subscriptions respectively.

### Verification
- `npx tsc --noEmit`, `npx eslint .`, `npm run build` — all clean (`/admin/subscription-plans`, `/admin/subscriptions`, `/dashboard/subscription`, `/dashboard/staff` all compile as new routes).
- Live checks against a running dev server + real Supabase data: logged in as the seeded Super Admin and the demo hotel owner via the real credentials flow; confirmed `/admin/subscription-plans`, `/admin/subscriptions`, `/dashboard/subscription`, `/dashboard/staff` all return 200 with correct content (the partner subscription page genuinely shows "Professional" / "ACTIVE" for the demo org, sourced from the database, not a placeholder).
- Directly exercised the limit-check query logic (the same Prisma calls `checkOrganizationLimit` makes) against real seeded data: demo hotel org (Professional, `maxProperties: 10`) → `{allowed: true, current: 1}`; demo car-rental org (Starter, `maxVehicles: 5`) → `{allowed: true, current: 2}`; (Starter, `maxBranches: 2`) → `{allowed: true, current: 1}` — confirms the limit arithmetic and Prisma field mapping are correct against live rows.
- Interactive browser form-submission testing (inviting staff, changing plans through the UI, hitting a limit at the boundary and seeing it actually block) was not completed this pass — the Chrome browser automation tool was unavailable for the whole session (see Phase 1 remediation report, same limitation).

### Known limitations
- No billing/payment integration yet — plan changes and the FREE-plan assignment are free of charge; a paid plan's `monthlyPrice`/`annualPrice` isn't actually charged anywhere yet. That's exactly what the Payments milestone (next) wires in — `renewSubscriptionAction` and the `PAST_DUE`/grace-period/`SUSPENDED` flow are built and ready for it to drive.
- No scheduled job yet enforces `currentPeriodEnd` expiry or advances `PAST_DUE` → `SUSPENDED` after the grace window — that requires the Payments milestone's retry/cron infrastructure.

## Milestone 2 — Payments

### What was built
- **Provider abstraction** (`src/domains/payments/providers/`): a `PaymentProvider` TS interface (`createPaymentIntent`, `refund`, `verifyWebhookSignature`, `parseWebhookEvent`) with 5 implementations — `stripe.ts` (real `stripe` SDK, new dependency), `paypal.ts` (thin `fetch`-based client over PayPal's v2 Orders API — PayPal's official Node SDK is deprecated), and `manual-providers.ts` (bank transfer / manual / cash-at-property, fully functional immediately, no external dependency — each creates a `PENDING` payment with instructions that staff confirm later). Stripe/PayPal auto-detect missing credentials (`STRIPE_SECRET_KEY`, `PAYPAL_CLIENT_ID`/`SECRET`) and run in a clearly-labeled sandbox/mock mode (deterministic `PENDING` result, no network call) rather than erroring — mirrors how MASTER-PLAN scopes Phase 3's channel-manager mock connectors. `registry.ts` exposes `getProvider(code)`.
- **Schema**: `Payment` (org/reservation/subscription-scoped, provider, status lifecycle `PENDING → AUTHORIZED/PAID/FAILED/CANCELLED/REFUNDED/PARTIALLY_REFUNDED`, retry tracking), `Refund`, `Invoice` (+ `InvoiceLineItem`, `CreditNote`; full Original-price/Currency/Taxes/Fees/Discount/Commission/Total breakdown, matching the customer-facing invoice fields MASTER-PLAN requires), `WebhookLog` (every webhook attempt is logged, even on invalid signature, for idempotency + audit).
- **Booking integration**: both booking forms (`hotel-booking-form.tsx`/`car-booking-form.tsx`) gained a real Payment-method selector (Card/PayPal/Bank transfer/Manual/Cash at property). `src/domains/payments/booking-payment.ts` (`createBookingPaymentAndInvoice`) runs right after a `Reservation` is created — outside its own transaction, since a provider call may hit the network — creating the real `Payment` + `Invoice` ledger rows and mirroring the result onto `Reservation.paymentStatus` via `src/domains/payments/sync.ts`. `Reservation.paymentMethod`/`paymentStatus` are kept as a denormalized fast-path snapshot (still read throughout the existing UI); `Payment`/`Invoice` are now the real financial ledger.
- **Backfill**: `prisma/scripts/backfill-payments.ts` — run once against the live Supabase database, created `Payment` + `Invoice` rows for the 2 pre-existing Phase-1 reservations (`PAY_AT_PROPERTY → CASH_AT_PROPERTY` mapping), so none were orphaned by the migration.
- **Webhooks**: `src/app/api/webhooks/stripe/route.ts` and `.../paypal/route.ts` (`runtime = "nodejs"`, required since Prisma's `@prisma/adapter-pg` needs Node, not Edge) — read the raw request body for signature verification, always write a `WebhookLog` row (even on failure), dispatch verified events to `src/domains/payments/webhook-handler.ts` which updates `Payment`/`Invoice`/`Subscription` status and re-syncs the linked `Reservation`. Idempotent via a `(provider, providerEventId)` lookup against `WebhookLog` before processing.
- **Retries**: `Payment.retryCount`/`nextRetryAt` fields + `src/app/api/cron/retry-failed-payments/route.ts`, a shared-secret-guarded (`CRON_SECRET`) Node route meant for an external scheduler — not a Redis/BullMQ queue, which is Phase 3 "Performance and Scalability" scope.
- **UI**: `admin/payments`, `admin/invoices` (with void), partner `dashboard/payments` (confirm bank-transfer/manual/cash payments, request refunds) and `dashboard/invoices`, all built on a shared `src/components/billing/invoice-view.tsx`.
- **Env**: `.env.example` documents `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`/`PAYPAL_CLIENT_ID`/`PAYPAL_CLIENT_SECRET`/`PAYPAL_WEBHOOK_ID`/`CRON_SECRET`, all optional.

### Verification
- `npx tsc --noEmit`, `npx eslint .`, `npm run build` — all clean (5 new routes: `admin/payments`, `admin/invoices`, `dashboard/payments`, `dashboard/invoices`, plus the 3 API routes).
- Ran `npx prisma migrate dev` against the live Supabase database, then `npx tsx prisma/scripts/backfill-payments.ts` — it found and correctly backfilled the 2 real reservations from Phase 1's original live-testing pass (verified the resulting `Payment` rows: `CASH_AT_PROPERTY / PENDING / 3080 MAD` and `CASH_AT_PROPERTY / PENDING / 1950 MAD`, matching the exact amounts recorded in `PHASE-1-COMPLETION-REPORT.md`'s original test pass).
- Live HTTP checks against a running dev server with real Supabase data: `admin/payments`/`admin/invoices` (Super Admin session) and `dashboard/payments`/`dashboard/invoices` (demo hotel-owner session) all return 200 and render the real backfilled invoice numbers/statuses, not placeholders.
- Sent an intentionally-unsigned request to `/api/webhooks/stripe` — confirmed it's rejected with 400 `{"error":"Invalid signature"}` (doesn't crash) and that a `WebhookLog` row was still written (`signatureValid: false`, `payload: {"note":"signature verification failed"}`), proving the audit-trail-on-every-attempt behavior.
- Interactive testing of a brand-new booking driving `createBookingPaymentAndInvoice` end-to-end (choosing each payment method in the UI, confirming a bank-transfer payment as staff, issuing a refund) was not completed this pass — Chrome browser automation was unavailable for the whole session. Confidence is otherwise high: the exact same Prisma calls are exercised (and verified correct) by the backfill script above, and `tsc`/`build` confirm every type across the new provider/webhook/booking-integration code compiles against the real generated Prisma client.

### Known limitations
- Stripe/PayPal are untested against real sandbox credentials (none were provided this session, per the user's choice to build adapter-ready code now) — the mock-mode code paths are exercised by the type/build checks and by code review, not a live test-mode charge.
- No automatic `Subscription` expiry/renewal job is scheduled yet — `renewSubscriptionAction` and `/api/cron/retry-failed-payments` exist and are wired correctly, but nothing calls them on a timer inside this app (expected: an external scheduler hitting the cron route, per the milestone's scope boundary).
- PayPal webhook signature verification requires `PAYPAL_WEBHOOK_ID`; without it (or without live credentials generally), `/api/webhooks/paypal` correctly always returns 400, matching Stripe's behavior when unconfigured.

## Milestone 3 — Affiliates

### What was built
- **Architecture**: an Affiliate is modeled as an `Organization` (type `AFFILIATE`), not a bare `User`-linked table — the schema already anticipated this (`OrganizationType.AFFILIATE` existed unused since Phase 1, and `registerSchema` already special-cased `AFFILIATE_PARTNER` to skip `organizationName`). `ORG_ROLE_TO_TYPE` now maps `AFFILIATE_PARTNER → AFFILIATE`, so registering as an affiliate reuses the exact same approval workflow, `requireOrganizationAccess` tenant isolation, and audit logging as hotel/car-rental partners — `registerAction` now also auto-creates the `Affiliate` row (with a generated referral code) inside its existing transaction, skipping the FREE subscription plan assignment (affiliates don't have hotels/vehicles/rooms to limit).
- **Schema**: `Affiliate`, `Campaign`, `AffiliateClick` (hashed IP, not raw), `Commission` (status lifecycle `PENDING → APPROVED/REJECTED → PAID`/`CANCELLED`, `reservationId` unique — double-crediting one booking is impossible at the DB level), `Withdrawal`, and a **separate** `AffiliateCommissionRule` table (deliberately not sharing the existing partner-facing `CommissionRule` — that table means "the platform's cut from the partner," a different concept from "what an affiliate earns for referring a booking to that partner").
- **Click tracking**: `src/app/[locale]/r/[code]/route.ts` — a dedicated redirect route (`/en/r/AB12CD34?camp=summer`), not query-param sniffing in the shared layout as originally sketched in the plan: Next.js layouts don't receive `searchParams` (only pages/route handlers do), so a redirect-link route is both the correct fix and the standard pattern for referral links. Sets a long-lived visitor cookie and a 30-day `TRAVLBOK_REF` cookie (last-click attribution), dedupes repeat clicks from the same visitor within a 4-hour window, and only proceeds past redirect for real affiliate codes.
- **Conversion**: `src/domains/affiliates/conversion.ts` (`recordAffiliateConversion`), called inside the same `$transaction` as both `createHotelReservationAction`/`createCarReservationAction` right after the `Reservation` row exists. Resolves the `TRAVLBOK_REF` cookie, requires the referring organization to be `APPROVED`, blocks self-referral (customer is a member of the affiliate's own organization — logged via `logAudit`), looks up the rate via `src/domains/affiliates/rate.ts` (`getAffiliateCommissionRate`, org-specific rule → platform default → 5% sensible fallback), and creates a `PENDING` `Commission` with `holdReleaseAt` from configurable settings.
- **Cancellation cascade**: `src/domains/affiliates/commission-lifecycle.ts`, hooked into both `cancelReservationAction` and `updatePartnerReservationStatusAction` — `PENDING`/`APPROVED` commissions auto-cancel when the booking is cancelled/refunded; an already-`PAID` commission is never auto-reversed, just flagged via `logAudit` for manual admin review.
- **UI**: partner side — `dashboard/affiliate` (referral link, click/conversion stats, pending/approved commission totals, payout method form), `dashboard/affiliate/campaigns` (create campaign links, client-rendered QR codes via the new `qrcode` dependency, activate/deactivate), `dashboard/affiliate/withdrawals` (request a withdrawal — blocked below the configured minimum or before the holding period releases), `dashboard/affiliate/promo-materials` (reuses the existing `FileDropzone`/upload stack with a new `PROMO_MATERIAL` upload purpose). Admin side — `admin/affiliates` (affiliate list + pending-commission approve/reject; org approval itself is already covered by the existing `admin/organizations` screen, which works generically over any organization type including `AFFILIATE`), `admin/affiliates/commission-rules`, `admin/affiliates/settings` (minimum withdrawal, holding period), `admin/withdrawals` (approve/reject/mark paid). The `/affiliate` marketing page's "coming soon" notice was removed now that the program is real.

### Verification
- `npx tsc --noEmit`, `npx eslint .`, `npm run build` — all clean (10 new routes, including the `/r/[code]` redirect route).
- Live end-to-end test against the running dev server + real Supabase database: created a test `Affiliate`/`Organization`/`User` directly (approved, so conversion isn't blocked), hit `GET /en/r/<referralCode>` with curl, and confirmed: a 307 redirect to `/en`, a `TRAVLBOK_VISITOR` cookie set, and a `TRAVLBOK_REF` cookie set containing the correct `affiliateId`/`clickId` JSON — then queried the database directly and confirmed the matching `AffiliateClick` row was really persisted (`ipAddressHash` populated with a SHA-256 hash, not a raw IP; `landingPath: "/en"`). Test data was cleaned up afterward.
- Directly verified `getAffiliateCommissionRate`'s query logic against a real organization with no configured rule: correctly falls back to the 5% platform default.
- Live HTTP checks (Super Admin session): `admin/affiliates`, `admin/affiliates/commission-rules`, `admin/affiliates/settings`, `admin/withdrawals` all return 200.
- Not completed this pass (Chrome browser automation unavailable all session, as in the prior two milestones): driving an actual booking through the UI with a `TRAVLBOK_REF` cookie present to see a `Commission` row appear, requesting a withdrawal through the partner UI, and the admin approve/reject click flow. The exact code paths involved (cookie parsing, self-referral check, rate lookup, `Commission` creation) are the same ones exercised by the live click-tracking test above and by `tsc`/`build`, so confidence is high, but this specific chain wasn't driven end-to-end interactively.

### Known limitations
- `AffiliateCommissionRule.organizationId` is a plain field, not a Prisma relation to `Organization` (unlike the partner-facing `CommissionRule`) — a deliberate simplification to avoid growing the already-large `Organization` model further; a rule referencing a deleted organization becomes a harmless orphan row rather than being cascade-deleted.
- No fraud detection beyond IP-hash-based click dedup and the self-referral organization-membership check — MASTER-PLAN's broader "fraudulent clicks" protection (e.g. velocity limits, bot detection) is not implemented.
