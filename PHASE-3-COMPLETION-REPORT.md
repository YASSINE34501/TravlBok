## Milestone 1 — Channel Manager

### What was built

**Provider abstraction** (`src/domains/channel-manager/providers/`): a `ChannelProvider` TypeScript interface (`testConnection`, `pushAvailability`, `pushRates`, `pushRestrictions`, `pullReservations`, `pushCancellation`) covering every MASTER-PLAN sync category. None of the six named channels (Booking.com, Expedia, Airbnb, Agoda, Hotels.com, Vrbo) expose a public self-serve API — connecting one for real requires a signed partner agreement and an official SDK/API contract that doesn't exist for this project. This is a materially different situation from Phase 2's Stripe/PayPal, where a real SDK and public sandbox exist. Per MASTER-PLAN's explicit instruction ("Do not create fake production integrations... Actual API connections enabled only with official partner credentials"), `providers/mock-provider.ts` implements one honest, parametrized simulated adapter (`createMockProvider(code)`) shared by all seven provider codes (the six named channels plus an explicit `MOCK_SANDBOX` for testing) — no network calls, deterministic and logged results, clearly labeled as simulated everywhere it surfaces in the UI. `registry.ts` exposes `getChannelProvider(code)`; swapping in a real adapter later (once a partner agreement exists) means implementing the same interface and changing one registry line — no calling-code changes.

**Secure credential storage**: `src/lib/crypto/secrets.ts` — real AES-256-GCM encryption/decryption (Node's built-in `crypto`, no new dependency), keyed by `CHANNEL_CREDENTIALS_ENCRYPTION_KEY` if set, or derived from `AUTH_SECRET` otherwise so it works out of the box in development. `ChannelConnection.credentialsCiphertext`/`credentialsIv` store the encrypted blob; credentials are never persisted in plain text.

**Schema** (`prisma/schema.prisma`): `ChannelConnection` (one per hotel+provider, status `DISCONNECTED/CONNECTED/ERROR`, auto-generated per-connection `webhookSecret`, `autoSyncEnabled`, `lastSyncedAt`/`lastErrorMessage`), `ChannelRoomMapping` (room type ↔ external room/rate-plan ID), `SyncJob` (`type`: `AVAILABILITY/RATES/RESTRICTIONS/RESERVATION_IMPORT/FULL`, `direction`: `PUSH/PULL`, `status`: `PENDING/PROCESSING/COMPLETED/FAILED/PARTIAL/CONFLICT` — the exact statuses MASTER-PLAN specifies), `SyncLogEntry` (per-job granular log lines, `INFO/WARN/ERROR`), `ChannelReservationImport` (**the idempotency mechanism** — unique on `(channelConnectionId, externalReservationId)`, so a retried or duplicate-delivered webhook can never create a second `Reservation`).

**Centralized inventory locking / overbooking prevention**: `src/domains/channel-manager/inventory.ts` (`computeDailyAvailability`) is the single source of truth for "how many rooms are free on this date" — it reads the exact same `RoomType`/`RoomAvailabilityOverride`/`ReservationRoomItem` tables the marketplace booking flow already uses (reusing `resolveNightlyPrice` from `src/domains/reservations/pricing.ts` for rate resolution). Because a channel-imported `Reservation` is a normal row in that same ledger, it's automatically counted by every other booking path — there's no separate per-channel inventory counter that can drift out of sync. This **is** the "centralized inventory locking" MASTER-PLAN asks for, achieved by not duplicating the inventory data model rather than by building a new locking layer.

**Conflict detection**: `src/domains/channel-manager/sync.ts` (`importExternalReservation`) runs the same Serializable-transaction overlap check the marketplace booking flow uses. If the channel's copy of availability was stale and importing would oversell the room, the booking is **still created** (the channel already confirmed it with the guest — refusing it would just hide the problem, not prevent it) but `ChannelReservationImport.hasConflict` is set with an explanatory note, surfaced prominently in both the partner and admin UI for manual review (`resolveConflictAction` marks it reviewed).

**Sync engine** (`sync.ts`): `runPushSync` (availability/rates/restrictions, run per active room mapping, logged as a `SyncJob` with per-row `SyncLogEntry`s), `runPullSync` (calls the provider's `pullReservations`, imports each via `importExternalReservation`), `notifyChannelsOfCancellation` (hooked into both `cancelReservationAction` and `updatePartnerReservationStatusAction` in `src/domains/reservations/actions.ts` — when a channel-sourced booking is cancelled on our side, the channel is notified via `pushCancellation`).

**Payment integration**: imported reservations get a real `Payment`/`Invoice` via Phase 2's `createAdHocPaymentAndInvoice` (provider `MANUAL` — OTA-collected payment is reconciled by finance, consistent with how PMS walk-ins already use the same ad-hoc payment path). No new payment concept was introduced.

**Gating**: every Channel Manager action/route checks `hasFeature(organizationId, "featureChannelManager")` — the same helper from the Subscriptions milestone. `prisma/seed.ts`'s plan seeding now also **updates** (not just creates) feature flags on existing `SubscriptionPlan` rows so this rollout takes effect without a manual DB edit; Professional/Business/Enterprise plans have it enabled, Free/Starter don't.

**Webhook + cron infrastructure**: `src/app/api/webhooks/channels/[provider]/route.ts` — a real, legitimate infrastructure endpoint (per-connection `webhookSecret` verified with `crypto.timingSafeEqual`) that no real channel currently calls (none offer self-serve webhook registration), but is shaped to accept a generic reservation-notification payload so a future real adapter's webhook can be pointed at it without changes. `src/app/api/cron/channel-auto-sync/route.ts` — `CRON_SECRET`-guarded, meant for an external scheduler (same pattern as Phase 2's payment-retry cron), iterates connections with `autoSyncEnabled` and runs a full push + pull.

**UI**:
- Partner (`dashboard/channels`, HOTEL orgs only): connect a channel (provider + hotel + credentials, with a note that no live credentials are needed to test), per-connection cards (status badge, manual push/pull sync buttons, auto-sync toggle, disconnect), room mapping (add/remove), a **simulate incoming reservation** form (exercises the real import pipeline without needing a live webhook), a conflicts-needing-review panel, and a sync-history page (`dashboard/channels/[connectionId]/sync-jobs`).
- Super Admin (`admin/channels`): platform-wide connection list with active/conflict/failure counts, force-disconnect, and a recent-sync-jobs feed across every organization.

## Milestone 2 — Dynamic Pricing Engine

### What was built

**Rule-based engine, no external AI** (`src/domains/dynamic-pricing/engine.ts`): a pure, side-effect-free `applyPricingRules(basePrice, context, rules, bounds)` that matches every MASTER-PLAN price factor (`PricingRuleFactor`: `SEASON`, `DAY_OF_WEEK`, `WEEKEND`, `HOLIDAY`, `SPECIAL_EVENT`, `OCCUPANCY`, `REMAINING_INVENTORY`, `BOOKING_WINDOW`, `LENGTH_OF_STAY`, `DEMAND_LEVEL`) against a per-night `PricingContext`, applies every matching rule in ascending `priority` order (rules stack — an occupancy surcharge and a weekend surcharge can both fire the same night), and **always** clamps the result to `RoomType.minPrice`/`maxPrice` centrally — MASTER-PLAN's "never breach min/max prices" is enforced once in this function, never trusted to individual rules. `DEMAND_LEVEL` is derived deterministically from occupancy buckets (`deriveDemandLevel`: <40% LOW, 40–75% MEDIUM, >75% HIGH) — no ML/external scoring.

**Schema** (`prisma/schema.prisma`): `PricingRule` (scoped to a `Hotel`, optionally to one `RoomType` — `roomTypeId: null` applies to every room type in the hotel; `priority`, `activeFrom`/`activeTo` activation window, `requiresApproval`/`approvalStatus` for the staff approval workflow, soft-deletable), `DynamicPriceLog` (unique on `(roomTypeId, date)` — the materialized pricing calendar / price history, `source: LIVE | RECALCULATED` distinguishes a real booking's price from a forward-looking bulk recalculation). `RoomType` gained nullable `minPrice`/`maxPrice` columns (the min/max price factor) and a min/max-price pair was added to the existing room create/edit form (`RoomForm`) and its `roomSchema`/`buildRoomData`.

**Resolution pipeline** (`src/domains/dynamic-pricing/resolver.ts`, `occupancy.ts`): `getApplicableRules` fetches only rules that are `isActive`, `approvalStatus: APPROVED` (a `requiresApproval` rule stays `PENDING` and is invisible here until a manager approves it), and inside their activation window. `getStayOccupancy` computes one aggregate occupancy/remaining-inventory figure for an entire stay — the same whole-stay-aggregate simplification the marketplace's existing overbooking check in `reservations/actions.ts` already makes (documented there, not a new deviation). `computeDailyOccupancy` computes accurate per-day occupancy for the pricing calendar. `getStayDynamicPricing` is the single convenience entry point both the price-preview and real-booking paths call: checks the org's `featureDynamicPricing` flag, resolves occupancy, and returns a per-night detail map (empty when the plan doesn't include Dynamic Pricing, so callers never need an `if` branch).

**Wiring into the existing pricing pipeline** (`src/domains/reservations/pricing.ts`, `preview.ts`, `actions.ts`): `calculateHotelPriceBreakdown` gained an optional `nightlyPriceOverrides?: Map<dateKey, number>` parameter — when a night is present in the map it wins over the existing season/base calculation; a night is **never** present when it has a manual `RoomAvailabilityOverride.priceOverride` (the engine skips those nights entirely), so **a staff manual override always wins over dynamic pricing**, verified explicitly. This is the only change to the existing pricing function — fully backward compatible, every other caller (car pricing, channel-manager's rate display) is untouched. `previewHotelPriceAction` and `createHotelReservationAction` both now compute `getStayDynamicPricing(...)` and feed it in; after a real booking commits, `logDynamicPricesForBooking` (`src/domains/dynamic-pricing/log.ts`) best-effort-persists a `DynamicPriceLog` row (`source: LIVE`) for each adjusted night — swallows its own errors so a logging failure can never fail the booking.

**Scope decision**: Dynamic Pricing applies to hotel room types only (not car rentals) and to the marketplace/PMS booking pipeline only — Channel Manager's rate push (`channel-manager/inventory.ts`) is intentionally left reading the static season/base price this pass, to avoid touching already-verified Milestone 1 code; documented as a known limitation below, not silently skipped.

**Staff approval workflow, simulation, bulk update, pricing calendar** (`src/domains/dynamic-pricing/actions.ts`): `createPricingRuleAction`/`updatePricingRuleAction` (editing a `requiresApproval` rule always resets it to `PENDING` — a manager re-approves exactly what they're signing off on), `approveRuleAction`/`rejectRuleAction` (restricted to `HOTEL_OWNER`/`HOTEL_MANAGER`), `archivePricingRuleAction`, `toggleRuleActiveAction`. `simulatePricingAction` runs the identical engine for a hypothetical stay **without** writing `DynamicPriceLog` — true simulation mode. `recalculatePricingCalendarAction` is the bulk-update / forecast-data path: recomputes and upserts a `DynamicPriceLog` row for every night in a date range using real per-day occupancy, powering the pricing calendar and revenue-comparison views (`queries.ts`: `getPriceHistory`, `getRevenueComparison`) without waiting for real bookings. Every mutation is `logAudit`-recorded. Super Admin oversight: `adminSetRuleStatusAction` plus `admin/pricing` (platform-wide rule list, pending-approval count, approve/reject).

**Gating**: every action/route checks `hasFeature(organizationId, "featureDynamicPricing")` — the same helper from Subscriptions. Found and fixed the same seed gap Channel Manager hit: `featureDynamicPricing` existed on the `SubscriptionPlan` model since Phase 2 but `prisma/seed.ts` never set it on any plan (stayed `false` everywhere). Fixed by adding it to the plan-seeding data (Professional/Business/Enterprise: `true`) and to the existing update-in-place upsert, verified live (Riad Atlas demo org, Professional plan, went from "not included in your plan" to the full form after reseeding).

**UI**: Partner (`dashboard/pricing`, HOTEL orgs only): pending-approval panel, create-rule form (`PricingRuleForm` — factor-conditional fields: threshold+operator for occupancy/inventory/booking-window/LOS, day checkboxes, date range, demand level), rule list with active/approval badges and approve/reject/activate/archive actions, and a combined simulate + recalculate-calendar panel (`PricingCalendarPanel`) showing a per-night base-vs-final price table. Super Admin (`admin/pricing`): platform-wide rule list with active/pending/total counts and approve/reject.

## Milestone 3 — Multi-Property & Multi-Branch Management

### What was already in place (audited, not rebuilt)
An organization could already own multiple `Hotel`s / `CarBranch`es (Phase 1), `dashboard/bookings` and `dashboard/payments` already query by `organizationId` (already org-wide/central across every property — no per-hotel silo existed to fix), `dashboard/staff` already manages `OrganizationMember` org-wide ("Central staff"), and `Subscription.organizationId` is `@unique` — one subscription already covers every property under an org ("Group subscriptions"). This pass built the genuinely missing pieces: property/branch **comparison and consolidated financial rollups**, explicit **fleet transfer** and **insurance/maintenance tracking**, and **branch-level staff scoping** (none of these existed before, confirmed by reading every relevant page/action file first).

### What was built

**Hotel groups — property comparison & consolidated revenue** (`src/domains/hotels/analytics.ts`, `dashboard/properties/comparison`): `getPropertyComparison(organizationId)` rolls up `HotelReservationLink` + `ReservationRoomItem` for CONFIRMED/COMPLETED bookings into per-hotel revenue, booking count, nights sold, ADR, and average approved-review rating; the comparison page adds a consolidated-revenue/total-bookings summary on top and links out to the already-central Bookings/Staff pages rather than duplicating them. A "Compare properties" button appears on `dashboard/properties` once an org has more than one hotel.

**Car rentals — fleet transfer, insurance & maintenance tracking**: `Vehicle` gained `insuranceExpiryAt`/`lastMaintenanceAt`/`nextMaintenanceDueAt` (nullable `Date` columns, additive). `transferVehicleAction` (`src/domains/vehicles/actions.ts`) is a dedicated action — separate from the general edit form — that changes `branchId` and writes an explicit `logAudit` entry with both `fromBranchId`/`toBranchId`, giving fleet-location a real history (no new table needed; `AuditLog` is the platform's existing audit trail). The vehicle detail page shows a "Fleet location" transfer control (owners/unscoped staff only) and destructive-styled "Insurance expiring soon" (<30 days) / "Maintenance overdue" badges; the vehicles list shows a compact "Needs attention" badge per card.

**Car rentals — branch revenue/utilization** (`src/domains/branches/queries.ts`): `getBranchPerformance` computes, per branch, vehicle count, currently-rented count, a utilization % (rented/total — a snapshot, not a time-windowed rate), and revenue (`CarReservationLink` → CONFIRMED/COMPLETED `Reservation.totalAmount`). Surfaced on both the branches list (compact) and branch detail page (a stats card).

**Car rentals — branch staff permissions** (`OrganizationMember.branchId`, nullable, `src/domains/branches/access.ts`): `getScopedBranchId(organizationId, userId, role)` returns `null` (unscoped — sees/manages every branch) for owners and platform staff, or for `CAR_RENTAL_STAFF` with no branch assigned; otherwise returns the one branch they're restricted to. This is **enforced**, not just displayed: `vehicles/page.tsx` and `branches/page.tsx` filter their lists by the scope, `vehicles/[vehicleId]`/`branches/[branchId]` `notFound()` a scoped staff member trying to open another branch's page directly by URL, and `createVehicleAction`/`updateVehicleAction`/`createBranchAction`/`updateBranchAction` re-check the scope server-side (a branch-scoped `CAR_RENTAL_STAFF` member can create/edit vehicles only in their own branch, and can't create/edit a `CarBranch` at all — opening or reassigning a whole branch stays an owner/manager decision). `transferVehicleAction` refuses branch-scoped staff outright — moving fleet across branches is deliberately unscoped-only. Assignment happens via a branch selector on `InviteStaffForm` (car-rental orgs only) and a per-row `StaffBranchSelect` on the staff page for existing members.

### Known limitations

- "Fleet location" tracking is branch-level (a vehicle's current branch, changed only through the explicit transfer action) plus the branch's existing static city/lat-lng — there's no live GPS tracking, consistent with MASTER-PLAN's phrasing ("Track fleet location") being about which branch a vehicle belongs to, not real-time telemetry.

## Milestone 4 — Advanced Analytics

### What was audited first
The existing Super Admin dashboard (`admin/page.tsx`) only showed simple lifetime counts (users, partners, hotels, one hardcoded-MAD revenue figure) with no date range, no filters, and no charts — none of MASTER-PLAN's 16 named metrics existed anywhere, and there was no chart library in `package.json` at all. `src/domains/pms/reports.ts`'s existing per-hotel ADR/occupancy/RevPAR formulas were read and **reused** (not reinvented) for the new platform-wide aggregate versions.

### What was built

## Milestone 6 — Security

### What was audited first
Of MASTER-PLAN's 16 named security items, only two were solidly in place beforehand: **secure password hashing** (bcrypt, cost 12) and **webhook signature verification** (Stripe via `stripe.webhooks.constructEvent`, PayPal via its server-to-server verify endpoint, both matching the rigor of Channel Manager's `timingSafeEqual` check). Everything else — 2FA, rate limiting, session revocation, device history, login alerts, audit logging *of logins specifically*, CSP/security headers, and API key management — was either completely absent or only half-scaffolded (the `AuditLog`/`Session` tables had the right columns but nothing populated them; the login path called `logAudit` for **nothing**, not even on failure). `session: { strategy: "jwt" }` was confirmed despite a `PrismaAdapter` being wired in, meaning `Session` rows are never written — ruling out "delete the Session row" as a revocation mechanism. **Data validation** (zod, everywhere), **audit logs** (already used by ~25+ call sites), **encrypted credentials** (Channel Manager's AES-256-GCM), **tenant isolation**, and **least-privilege** (RBAC role groups) were all already solid from earlier phases and needed no new work — CSRF for Server Actions turned out to already be handled by the Next 16 framework itself (Origin/Host header check, confirmed by reading `node_modules/next/dist/docs`, not assumed).

### What was built

**Security headers & CSP** (`next.config.ts`): the "without nonces" approach from Next's own CSP guide (a nonce-based policy would force every page in this large, mostly-statically-optimized marketplace into dynamic rendering) — `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, and `Strict-Transport-Security` (production only) applied to every route via `headers()`. `img-src https:` (not a fixed allowlist) matches the existing wildcard-HTTPS `images.remotePatterns`. Verified live: real `curl` response headers match exactly.

**Rate limiting** (`src/lib/rate-limit.ts`): a generic Postgres-backed fixed-window limiter (new `RateLimitBucket` model) — explicitly not Redis (none exists yet; "Redis-ready" is Phase 3 Performance/Scale prep, not a requirement to stand one up here), designed so swapping the backing store later means replacing one function body, not every call site. Applied to login (5/15min per email, 20/15min per IP — both checked inside the `authorize()` callback, which in this Next-Auth v5 version receives the raw `Request` and its headers), registration (10/hour/IP), password-reset requests, and resend-verification (5/15min/IP each).

**2FA** (`src/lib/auth/totp.ts`): hand-rolled RFC 6238 TOTP/RFC 4226 HOTP using only Node's built-in `crypto` — no new dependency for something this security-critical and this small, and it lets the exact bytes be verified against the official RFC 4226 Appendix D test vectors (see Verification below). New `User.twoFactorEnabled`/`twoFactorSecret`/`twoFactorBackupCodes` fields. Enrollment (`account/security`, `TwoFactorSettings`): generate secret → render QR (reusing the `qrcode` package already installed for affiliate campaign QR codes, this time server-side) → confirm a code → one-time display of 8 bcrypt-hashed backup codes. Login (`authorize()` in `config.ts`): if `twoFactorEnabled`, a missing/wrong code throws a custom `TwoFactorRequiredError extends CredentialsSignin` whose `code` the client (`login-form.tsx`) detects via `result.code` to reveal a code field and resubmit — a legitimate, documented Next-Auth v5 pattern, not a hack. A matched backup code is consumed (removed) on use.

**Session revocation** (no session-strategy change — too high-risk to touch this late, given it's the most critical path in the app): since sessions are JWT-only, "sign out everywhere" works by comparing each token's mint time (`session.user.loginAt`, set once in the `jwt` callback) against a new `User.sessionsInvalidatedAt` column, checked centrally in `src/lib/rbac.ts`'s `getCurrentUser()` — every `requireUser`/`requireRole`/`requireOrganizationAccess` call in the app gets this check for free, with one extra indexed `User` read per request.

**Device history & login alerts**: `logAudit` (`src/lib/audit.ts`) now actually accepts and writes the `ipAddress`/`userAgent` columns that already existed on `AuditLog` but no caller ever populated. Every login attempt is now logged (`auth.login`, `auth.login_failed`, `auth.login_failed_2fa`) with real IP/UA, surfaced as a recent-activity list on `account/security`. A login from an IP not seen in the user's last 10 successful logins triggers a `new_login_detected` notification (in-app + email, via Milestone 5's `notifyUser`) — a real login alert, not just a logged row.

**File upload hardening** (`src/lib/upload/validation.ts`): added `validateFileSignature` — real magic-byte signature checking (JPEG/PNG/WebP/PDF/MP4/QuickTime/WebM) against the file's actual leading bytes, closing the gap where `file.type` is a client-supplied, trivially-spoofable string that the existing MIME allowlist alone couldn't catch.

**API key management** (`ApiKey` model + `src/domains/api-keys/`): partner-facing key issue/revoke, gated behind `featureApiAccess` (the same flag that already existed on `SubscriptionPlan` but, per the Milestone 4 audit, gated nothing real). Keys are SHA-256 hashed (not bcrypt — high-entropy random tokens don't need slow hashing the way user-memorable passwords/backup-codes do) with only a `keyPrefix` shown after creation; the raw key is displayed exactly once. `verifyApiKey()` is real, callable infrastructure with no public REST endpoint wired to it yet — the same honest-scaffold reasoning as Channel Manager's provider adapters and webhook route.
